# Changelog

All notable changes to Token-Goat Mem are documented in this file. **This file is the canonical version history** — `package.json` mirrors the latest release; if a version string anywhere disagrees with this file, this file wins. Format follows Keep a Changelog. Token-Goat Mem follows Semantic Versioning starting at 1.0.

## [Unreleased]

### Added

- **A `tests/bundle/` tier that drives the built `dist/token-goat-mem.mjs` as a subprocess** -- CONTRIBUTING.md's own rule is that a command with no coverage against the built bundle fails the gate, and until now exactly one test in the suite executed it (`mem --version`); everything else drove `run()` in-process against transformed TypeScript. The new tier is deliberately small: an init/uninstall round trip asserting hand-formatted config files come back byte-identical (four-space indent, CRLF, no trailing newline, no empty containers left behind), and a remember/recall/forget smoke test guarding what only a real subprocess can see -- externals resolving at runtime, the esbuild `define`, native-module loading, exit codes, and stdout vs stderr. Verified by dropping `better-sqlite3` from esbuild's `external` list: 8 of the 9 new tests fail on that build while the in-process suite stays green.

- **The pre-commit gate CONTRIBUTING.md specifies is now a real hook** -- `npm run lint && npm run typecheck && npm run test:guards` was documented as the check to run before every commit, with no `.husky`, no `.git/hooks/pre-commit`, and no hook manager behind it; it was a convention someone had to remember to type, and a commit that skipped it was indistinguishable from one that passed. `.githooks/pre-commit` now runs it, enabled by a `prepare` script that points `core.hooksPath` at the directory on `npm install`. It stays deliberately narrow -- the guards tier is pure introspection with no I/O, so the hook is fast enough that nobody reaches for `--no-verify` out of habit, and `npm test` stays a pre-push concern. Verified by staging a deliberate type error and confirming the commit was refused.

### Fixed

- **A `mem import` that overlapped another by one fact lost every fact it was going to add** -- the duplicate-id check that decides whether to insert a fact ran in the classification pass, which is outside the transaction that takes the write lock. Two imports sharing one id could therefore both classify it as new; the loser then hit the `facts.id` primary key, and because that insert sits inside the batch transaction, the whole batch rolled back rather than the one row that was already there. The id is now re-checked under the write lock and recorded as an ordinary duplicate skip. Individual writers were always correctly serialized; it was the read backing the decision that sat outside the lock. The regression test reproduces the interleave exactly rather than racing two processes: `db` is proxied so the rival's insert lands on the first `db.transaction(...)` call, which is the line immediately after classification and immediately before the lock is taken.
- **Preservation tests could not see the formatting damage they existed to catch** -- the no-op and conflict-abort tests in `wiring.test.ts` asserted `toEqual` on parsed objects, which is blind to exactly the failure mode 0.2.6 shipped fixes for: an indent silently normalized from four spaces to two, a compact file exploded across lines, a trailing newline added or dropped. They now assert on bytes, and their fixtures are seeded non-canonically (four-space indent, compact and unterminated) so a reserialization is visible rather than incidentally equal.
- **Type-aware linting was being paid for and not collected** -- `eslint.config.js` set `parserOptions.project` for every `.ts` file, which is the expensive part, then extended the non-type-aware `recommended` preset. `recommendedTypeChecked` now runs on `src/**` (not `tests/**`, where the `no-unsafe-*` family fires ~57 times on fixtures that parse JSON into `any` and immediately assert on it -- a legitimate shape for a fixture). It found seven issues, all fixed: three type assertions the surrounding narrowing already made redundant, two `async` handlers with nothing to await (`guard` accepts `void | Promise<void>`, so the keyword bought nothing), and `new Array(n).fill(undefined)` inferring `any[]` and being silently assigned into a typed array in `importFromJson`. One rule is suppressed with its reasoning at the call site: `withTimeout` forwards a caller-supplied embedding backend's own rejection reason verbatim, and wrapping it in an `Error` would bury what the caller needs to diagnose it. The rule earning this on its own is `no-floating-promises`, which finds zero violations today -- verified biting on an unawaited database write.
- **Two runtime dependencies nobody used were installed on every machine** -- `zod@^4.4.3` sat in `dependencies` imported by zero lines of `src/` and absent from the shipped bundle, and `sqlite-vec@^0.1.9` sat in `optionalDependencies` referenced only by a comment, through six releases. Both are removed. `sqlite-vec` can return the day a concrete embedding backend actually loads it; nothing today can reach the `EmbeddingBackend` seam in `retrieval.ts`, so it was install weight for an unreachable path. Verified by installing the packed tarball into a clean prefix: neither package appears, and `--version`, `doctor`, and a remember/recall round trip all work.
- **CONTRIBUTING.md documented a runtime surface that was wrong in both directions** -- it named `zod`, which was unused, and omitted `jsonc-parser`, which is real, marked `external` in the esbuild config, and resolved from `node_modules` at runtime. A new guard (`tests/guards/dependencies.test.ts`) now fails when a declared runtime dependency is imported nowhere in `src/`, so an unused one cannot sit in the manifest unnoticed again.
- **Three integration docs told users to paste text `mem init` does not write** -- the doc/code consistency test added in 0.2.5 only ever matched ` ```json ` fences, so every markdown block mem writes went unchecked and drifted. `claude-code.md` appended an `(e.g. --subject package-manager --value pnpm)` example the installer never writes, directly under a line promising to show exactly what it writes; all three `AGENTS.md` docs opened with "This machine has token-goat-mem installed" where the installer writes "token-goat-mem is installed", and carried a parenthetical list of trust caveats the block does not contain. The check now compares each doc's markdown fence against the block `install()` actually wrote to disk, rather than against a source constant, so a defect in the marker wrapping cannot slip past it either.
- **`docs/integrations/copilot-vscode.md` contradicted itself about its own keybindings** -- its keybindings section correctly records the 0.2.4 move to the `Ctrl+K M` / `Ctrl+K R` chords and explains that the old pair was dropped for shadowing View: Problems and New Window, while its workflow walkthrough four sections later still told the reader to press `Ctrl+Shift+M` and `Ctrl+Shift+N`. The walkthrough is prose outside every fenced block, so neither the JSON nor the markdown consistency check could see it; a third check now asserts it names the keys the installer writes and not the superseded pair.
- **Nothing ran the checks on push, and nothing ran them on Windows** -- `.github/workflows/` held one file, triggered only by a `v*` tag or manual dispatch, whose steps were `npm ci` then `npm publish`; lint, typecheck, test and build ran only as a side effect of `prepublishOnly`, so a commit breaking any of them landed on `master` and surfaced at the next release, reported as "publish failed" without saying which check broke. The single job was `ubuntu-latest` only, while `src/` carries six explicit `process.platform === "win32"` branches and every platform-gated test in the suite is skipped on one platform or the other -- the four `db-permissions` tests never ran on the machine this project is developed on, and the one Windows-only wiring test never ran in CI. A new `ci.yml` runs lint, typecheck and the full suite as separate named steps on both platforms for every push and pull request.
- **`engines: { node: ">=18" }` was never exercised** -- and could not be, since vitest 4 requires Node 20 or newer, so the suite cannot run on 18 at all. That claim is about the shipped bundle, not the toolchain, so a second CI job builds the bundle on Node 18 on both platforms and drives it directly with no test runner: version, doctor, and a remember/recall round trip. It is the narrowest check that would catch a Node-20-only API reaching the artifact users install.
- **CONTRIBUTING.md described end-to-end coverage the suite did not have** -- it told contributors `npm test` "includes end-to-end tests that build and exercise the shipped `dist/token-goat-mem.mjs` bundle," which was true of a single test asserting `--version`. It now describes the three tiers that actually exist and says which one a new test belongs in.
- **The 0.2.6 note over-claimed comment preservation** -- "Comments and trailing commas survive in both directions" covered a paragraph spanning both config paths, but only `.vscode/*.json` is parsed as JSONC. `.claude/settings.json` is parsed as strict JSON, matching Claude Code's own format, and a commented one is refused with a conflict error rather than modified. The claim is now scoped to the path it holds for.

### Changed

- **`mem recall` now binds facts to the project they were captured in** -- `--root` reached only anchor evaluation, so the store was searched whole: standing in one project and running `mem recall` surfaced another project's decisions as if they were local. `--scope project` did not help, because it matched the scope *label* rather than the binding, narrowing to "scoped to some project" instead of "scoped to this one" -- so even the README's own `mem recall --root . --scope project` example returned the wrong project's facts. A `project` fact now surfaces only from its own root, a `path` fact only from a root containing its file, and `global` facts from anywhere, unchanged. The filter runs inside `retrieve` alongside every other filter rather than narrowing the SQL query, because a pre-filtered pool hides a fact's rival from contradiction resolution, whose reinstatement pass then reads that absence as "nothing contests this" -- and scope binding is the filter most likely to separate two rivals, since a contradiction is keyed on subject + scope. `mem recall --hint-format` already scoped this way; the two paths now agree.

## [0.2.6] - 2026-08-29

Every fix in this release is in `mem init` / `mem uninstall`. The documented promise for those two
commands is that uninstall reverses exactly what init wrote and leaves everything else alone; five
separate defects broke it, one of them by deleting the user's own text.

### Fixed

- **`mem uninstall` could delete a block of the user's own file** -- the per-tool marked block was located with a bare `indexOf(start)` / `indexOf(end)` pair, which pairs the *first* start marker with the *first* end marker even when they do not belong together. A hand-edit, an interrupted write, or a merge conflict can leave an orphaned `<!-- token-goat-mem:<tool>:start -->` behind with no end of its own; uninstall then paired that orphan with the end marker of the real block further down and removed every byte in between. In a CLAUDE.md shaped `# My notes` / orphan / *user prose* / real block, the user prose went with it. The block is now located by scanning every start marker and taking the first one that resolves to a complete pair, which is how the shared `AGENTS.md` block has always been located -- the per-tool path simply never got the same rule. A stray *end* marker sitting ahead of the real block no longer makes install append a second copy, either.
- **A reinstall never upgraded the shared `AGENTS.md` block's body** -- `codex`, `copilot-cli`, and `copilot-vscode` share one reference-counted block, and the writer returned early as soon as the tool was already named in `tools=`. A body written by an older version of mem was therefore left in place forever: the per-tool blocks were replaced with current text on every reinstall and this one silently drifted away from them. It is now rebuilt from the same constant every time, and returns the file untouched only when the rebuild is byte-identical.
- **`mem init` rewrote the formatting of files it does not own** -- `.claude/settings.json` was round-tripped through `JSON.stringify(parsed, null, 2)`, so a config indented with four spaces came back indented with two, with its key layout and any non-canonical spacing gone. `.vscode/tasks.json` and `keybindings.json` went through jsonc-parser's `modify` with a `formattingOptions`, which reformats the *entire containing array*, so a hand-written one-line `{ "key": "ctrl+q", "command": "noop" }` came back exploded across five lines. Neither file is mem's to restyle. Both paths now edit text rather than reserialize an object: `modify` with no formatting options yields a genuinely surgical edit that touches nothing else, and mem re-renders only its own inserted payload, at the document's own indent unit (tabs included) and line ending. Comments and trailing commas survive in both directions on the `.vscode/*.json` path; `.claude/settings.json` is parsed as strict JSON, matching Claude Code's own format, and a commented one is refused with a conflict error rather than modified.
- **`mem uninstall` left behind the containers `mem init` had created** -- installing into a `settings.json` with no hooks at all, which is the common case, created `hooks` and `hooks.SessionStart`; uninstall removed the hook group and stopped, leaving a `"hooks": { "SessionStart": [] }` husk. `tasks.json` had the same shape via `"inputs": []`. Uninstall now prunes an array or object that its own removals emptied. An empty hook array is inert, so pruning one a user happened to have written by hand costs them nothing.
- **`mem init` wrote LF into files authored with CRLF, and `mem uninstall` grew a blank line each time** -- the marked block was assembled with hard-coded `\n`, so installing into a CRLF-authored CLAUDE.md produced a file with mixed line endings, and rewriting the shared block's `tools=` line dropped the `\r` from it. Uninstall then looked for a literal `"\n\n"` separator it would never find in such a file and left the surrounding blank lines in place, so each install/uninstall cycle added one. Every write now detects and preserves the file's own line ending, and the separator inserted by install is exactly the one removed by uninstall -- so a file with no trailing newline no longer gains one, and a whitespace-only file is no longer emptied.
- **The repository's own tracked files can no longer be checked out as CRLF** -- a `.gitattributes` with `* text=auto eol=lf` pins them. Under `core.autocrlf=true`, which is the Windows default, `docs/integrations/copilot-vscode.md` arrived with CRLF on all 161 lines, and the doc/code consistency test added in 0.2.5 parses that file with a `/```json\n/` regex that cannot match `\r\n`. That is a test that fails for a reason having nothing to do with what it tests, on a checkout that is otherwise correct.
- **The dry run described a shared-block install it was no longer doing** -- now that a reinstall refreshes a stale body, a tool already named in `tools=` can have work to do, and `mem init --dry-run` still reported it as "install would join existing shared block (adds `<tool>` to tools=)". That case now says it would refresh the body.
- **The `npm audit` note in CONTRIBUTING.md described advisories that no longer exist** -- it documented five dev-only advisories in the esbuild/vite/vitest chain and the reasoning for not forcing the fix. The toolchain upgrade that cleared all five landed before 0.2.5; `npm audit` has reported zero since, and the paragraph telling contributors otherwise outlived it.

### Added

- **Nine regression tests that assert on file bytes, not parsed structure** -- the formatting damage above was invisible to the existing suite because every assertion went through `JSON.parse`, and the round-trip leaks were worse than invisible: two tests had encoded the leftover empty containers as the expected result, one of them inside a test named "uninstall returns the file to its pre-install state". The new tests seed hand-formatted fixtures -- four-space, tab-indented, single-line, comment-carrying, CRLF -- and compare the file to itself after an install/uninstall cycle. Five were verified failing against the previous implementation before the fix landed.
- **Three regression tests for malformed and stale markers** -- an orphaned start marker ahead of a real block, a stray end marker before one, and a shared block whose body was written by an older version. Each was verified failing first.
- **A `## Line endings` section in CONTRIBUTING.md** -- explains what `.gitattributes` pins, when to run `git add --renormalize .`, and the distinction that matters here: files mem *edits* are the user's, and code that writes them must never hard-code `\n`.

## [0.2.4] - 2026-08-28

### Fixed

- **`mem review` and `mem show` now evaluate an anchor against the fact's own root, the way `mem recall` already did** — a project-scoped fact carries the root its anchor is meaningful relative to, but these two commands resolved the predicate against wherever they happened to be run. Running `mem review` from an unrelated checkout therefore produced a confident `contradicted` for a perfectly valid fact and listed it under the one heading that invites the user to forget it, while `mem recall` simultaneously affirmed the same fact. `mem show` had the mirror-image bug through a different door: with no `--root` it fell back to `fact.scopeRoot`, which for a `path`-scoped fact is a *file*, and resolving a predicate beneath a file path can only fail. Both now use the same `anchorRootFor` helper retrieval has used since the scope-root fix, so the three surfaces can no longer disagree about one fact.
- **`--since-epoch` no longer promotes a withheld fact to ground truth** — the epoch window was applied as a SQL filter on the candidate pool, before contradiction detection ran. Detection decides by comparing rivals, so a pool narrowed to one epoch left the surviving half of a contested pair standing alone, and the reinstatement pass read the absence of a rival as "nothing is left to contest this" and un-contested it. `mem recall --since-epoch N` surfaced as settled fact exactly what `mem recall` was withholding, and `mem review --since-epoch N` reported `contested: 0` for the same pair. Detection now runs over the whole store on both paths and the window is applied afterwards, as the display filter it was always meant to be.
- **A superseded fact restored from an old export is no longer deleted by the next `mem epoch --gc`** — the 90-day retention window is measured from `status_changed_at`, and a `mem export` envelope carries no status timestamp to restore. Starting that clock at the envelope's backdated `captured_at` meant every restored superseded fact arrived with its window already elapsed, so the first gc after a restore destroyed it: silent data loss on the one path the docs recommend for backups. A fact's status clock now starts at `captured_at` only when the status is `active` (where the two genuinely are the same moment, and where starting later would make a freshly-pinned fact instantly due for re-confirmation); every other status starts at the time of the write.
- **`mem recall` prints a fact id again** — 0.2.2 replaced the per-line CTA with a single footer, and the CTA was the only thing printing an id. The footer went on saying `mem show <id> for detail` while no `<id>` appeared anywhere in the output, so following the instruction required first running `mem list` to look up an id the command that asked for one had declined to print. Each result now leads with an 8-character prefix, the same git-style short form `mem show` already resolves.
- **`updateFact` now trims `text` and `value`, as `insertFact` always has** — the same content arrived normalized or not depending on which door it came through. Not cosmetic: `value` is half the contradiction key, so `" yarn "` and `"yarn"` were two distinct values to the detector and an edit that should have superseded a rival silently failed to match it.
- **The `--hint-format` seam now selects `prior_status`** — its row mapper had drifted from storage's. `resolveContradictions` reads that column to restore `pinned` when it reinstates a fact whose rival is gone, so on the hint path every reinstatement landed on `active`, stripping a pinned fact of its decay exemption. Latent today, since the TGMEM line encodes neither trust level nor pinned state, but it is real input to retrieval on the one surface another tool consumes programmatically.

### Changed

- **The VS Code keybindings `mem init` installs no longer shadow two editor defaults** — `ctrl+shift+m` (View: Problems) and `ctrl+shift+n` (New Window) were bound outright, and since a later entry in `keybindings.json` wins, installing mem quietly took both away. They are now the chords `ctrl+k m` and `ctrl+k r`: `ctrl+k` is VS Code's conventional extension prefix, so a second keystroke follows and the binding collides with far less. `mem uninstall` removes the old pair by its stamp, so an existing install is replaced rather than accumulated.


## [0.2.3] - 2026-08-27

### Security

- **The database and its home directory are no longer left to the umask** — `openDb` created `~/.mem` and `mem.db` with no explicit mode, so under a default umask of 022 they landed at 0755 and 0644: readable by every local account on a shared machine. Facts are exactly the data that must not be, since capture-time secret screening targets credentials and says nothing about the project internals and personal detail a fact legitimately contains. The home is now 0700 and the database 0600, applied before the WAL pragma runs so SQLite's `-wal`/`-shm` sidecars -- which hold the same rows -- inherit the restriction rather than the umask, and re-applied to an existing home so upgrading repairs a directory an earlier version created world-readable. Best-effort and POSIX-only: a chmod that is refused must not take the CLI down with it, and on Windows `chmod` toggles only the read-only bit while the profile ACL already restricts the file.
- **The `.git` machinery is no longer followed through a symlink** — every other file-touching anchor refuses a symlink at any path component, but the git predicates were exempt: a symlinked `.git`, or a `.git` file whose `gitdir:` pointer resolved to a symlink, redirected the subsequent `HEAD` and `index` reads to a path of the link's choosing. Root-containment is not available here -- submodules and worktrees legitimately keep their gitdir outside the working tree, so enforcing it would break real repositories -- but symlink refusal is, and it costs nothing a real layout depends on. A refused link yields `unverified`, never a fabricated verdict.
- **Both git reads are now size-capped before the read, not after** — `.git/index` was read whole into memory and only then checked against `MAX_GIT_INDEX_ENTRIES`, so the bound arrived after the allocation it was supposed to prevent; the `.git` pointer file had no bound at all. The index is now capped at 32 MB (a 100k-file tree indexes at roughly 10 MB, so no real repository is affected) and the pointer file at 4 KB, both from `statSync` before any `readFileSync`. Over the cap is `unverified`: the parse cannot be completed confidently, so no verdict is claimed.
- **The TGMEM emitter no longer trusts a fact id it did not write** — a line puts `id` in an unquoted, whitespace-delimited field, so an id carrying a newline could forge an entire second line in the consumer's parse. `display` is JSON-encoded and immune; `id` cannot be quoted without breaking the published wire contract, so the emitter drops any id containing whitespace or a control character and logs it, leaving well-formed neighbours untouched. No supported write path produces such an id (mem writes a `randomUUID`, and `import --from-json` validates), which is precisely why the check belongs at the emitter: it is the boundary that reads a database another version, or a person, may have written.
- **The atomic config write no longer widens a restrictive file's permissions** — `writeManagedFile` replaces the inode rather than updating it, so the replacement carried whatever the umask gave it. Adding mem's block to a `~/.claude/settings.json` the user had deliberately set to 0600 silently made it world-readable. The target's mode is now captured before the write and applied to the temp file before the rename.

### Changed

- **`SECURITY.md` no longer claims outstanding dev-dependency advisories** — those were cleared in 0.2.2 (esbuild 0.24 to 0.28, vitest 2 to 4); `npm audit` reports zero across prod and dev.

## [0.2.2] - 2026-08-27

### Added

- **`mem review --promote` / `--reject` resolve contested facts, not just pending ones** — `contested` is a withheld status a human is expected to arbitrate, but the review loop only ever accepted `pending` ids, so the one command documented as the resolution path refused the very facts it was listing. Promoting a contested fact now declares it the winner of its ambiguous contradiction and supersedes exactly its bucket rivals (via a new exported `sameContradictionBucket`, so review and the detector agree on "same bucket" by construction rather than through a second, drifting definition) — without that, the next detection pass would find the same tie and re-contest the group, making the promotion silently self-undoing. Rejecting one side re-runs reconciliation immediately, so the survivor is reinstated without waiting for the next `mem epoch --gc`. A winner that was pinned before the contradiction returns to `pinned`, never quietly demoted to `active`.
- **`facts.status_changed_at` and `facts.prior_status`** — two nullable columns (idempotent `ALTER`, no backfill) recording when a fact entered its current status and what it held immediately before. `status_changed_at` advances on every status write, including a re-write to the same value, because re-pinning *is* the act of re-confirmation; `prior_status` moves only on a genuine transition, so re-pinning cannot erase the status a later reinstatement needs. Readers treat an absent value as unknown and fall back to `captured_at`, which is exactly what the affected clocks used before, so pre-existing rows are judged no differently than they already were.
- **`unanchored` review bucket** — `mem review` gained a fifth bucket listing ground-truth facts that carry no anchor but whose text names something an anchor could be written against (a path, a URL, or a conventionally-bare config filename such as `package.json`). Closes a real blind spot: an anchorless fact short-circuits to `unverified` in `evaluateAnchor`, so it could never reach the `contradicted` bucket, and no other bucket claimed it either — an environment-dependent fact captured without an anchor sat at `unverified` indefinitely, invisible to both `mem review` and `mem doctor`, however thoroughly the world had moved on beneath it. The bucket is a nudge, not a pending decision: nothing is withheld from ground truth and no status changes. `--section unanchored` and the `--summary` counts include it; `preference` facts are excluded by construction, since no filesystem predicate can confirm or deny a judgment claim that merely happens to mention a path. Backed by a new pure, IO-free `mentionsAnchorableTarget` predicate in `src/anchors.ts`, deliberately conservative so ordinary prose ("we standardised on Node.js", "use and/or sparingly", "runs 24/7") cannot flood the bucket — it nominates only what it can recognise with confidence, and misses a fact that names a bare directory rather than a path.

### Changed

- **`mem pin <id>` refuses any withheld status instead of laundering it into maximal trust** — pinning is a promotion to decay-exempt ground truth, so it is now gated exactly like `mem review --promote`. Previously an id copied out of `mem list` was a side door around every withheld state: a `pending` suggestion — never reviewed by a human, the one invariant `captureSuggested` hardcodes its status to protect — went straight to maximal trust, and a `superseded` or `contested` fact that recall was deliberately withholding could be resurrected the same way. The error names the status and points at the command that can actually resolve it. Pinning an already-pinned fact remains a success, since that is how the re-confirmation nudge is cleared.
- **Documentation corrected to match the code** — `captureSuggested` was described as "not yet exposed as a CLI command" although `mem suggest` has shipped since 0.2.1, and the `sources` table was documented as a live audit trail although nothing in the capture path writes to it (its schema, storage API, `mem show --json` surfacing, and gc pruning all exist and are tested; the table is simply empty in practice). Both now say what is true.

### Fixed

- **`contested` was a trapdoor, not a status** — `detectContradictions` excluded `contested` facts from its candidate pool, and `mem review` queried only `active`/`pinned`. Together those made the status unfalsifiable: the pass that wrote it could never see it again, so a fact stayed withheld from ground truth forever even after the rival that caused the contradiction was forgotten, edited into agreement, or superseded — and `mem review --summary` reported `contested: 0` while `mem recall` was still withholding the fact. Detection now includes `contested` (a cached outcome of this detector, not an independent lifecycle state), emits nothing new while the contradiction genuinely stands, and reinstates a fact once nothing is left to contest it — restoring `pinned` where `prior_status` says the fact was pinned. `mem epoch --gc` and review's contested resolution share one `reconcileContradictions` helper, so they cannot disagree about which facts are still contested.
- **Retention clocks measured the wrong age** — the 90-day superseded-fact GC window and the pin re-confirmation nudge both keyed on `captured_at`, which never moves. A fact captured 91 days ago and forgotten yesterday was pruned on the very next pass, destroying the audit trail the soft delete exists to preserve, and the 1000-row cap kept the most recently *authored* facts rather than the most recently superseded ones. The pin nudge was worse: nothing a user could do changed when a fact was captured, so once due it nagged forever. Both now key on `status_changed_at`.
- **Project-scoped anchors were evaluated against the caller's root** — a `scope="project"` fact carries the project root it is bound to in `scope_root`, but `retrieve` evaluated every anchor against the querying root. Recalling from any other directory turned a perfectly valid fact into `contradicted` — the strongest verdict, the one that actively withholds a fact as wrong — purely because the query came from elsewhere. Only `project` scope is redirected; `path` and `global` keep the caller's root, since `scope_root` is only documented as an absolute project root directory for `project`.
- **Read-then-write transactions could fail unretryably under WAL** — every `db.transaction()` that reads before writing was invoked with better-sqlite3's default deferred `BEGIN`, which takes the write lock at the first write rather than the first read. A concurrent writer landing in that window invalidates the snapshot and SQLite fails the transaction with `SQLITE_BUSY_SNAPSHOT`, which — unlike plain `SQLITE_BUSY` — `busy_timeout` does not retry. All such sites now use `tx.immediate()`. Because an inner `db.transaction()` degrades to a `SAVEPOINT` when an outer one is open, the outer invocation is what decides the whole nest's locking mode; a source-level guard test (`tests/guards/transactions.test.ts`) now fails on any bare `tx()` invocation, since a behavioural test would have to lose a real race to notice a regression here.
- **Secret screening missed a hex secret sitting next to its own keyword** — a 40-hex-character string is exactly a git SHA-1, so the entropy fallback deliberately allowed it, which meant an `api-key` or `signing_key` named in prose next to its hex value was stored verbatim. A new `secret-keyword-hex` pattern reads the surrounding keyword (`password`, `secret`, `api_key`, `access_token`, `auth_token`, `signing_key`, …) rather than the shape, since length alone cannot tell a commit hash from a hashed credential. Separately, the hash allowlist matched any all-hex token of any length; it is now restricted to the canonical digest lengths (32/40/64). A bare commit hash is still stored untouched.
- **Anchors ignored the case sensitivity of the filesystem they ran on** — `glob-exists` and `git-tracked` matched case-sensitively everywhere, so on Windows an anchor naming `readme.md` returned `contradicted` for a `README.md` that plainly exists. Folding is enabled on win32 only, deliberately: macOS ships case-sensitive APFS volumes too, and folding there would trade a false `contradicted` for a false `affirmed`, which is the worse error under the three-valued-verdict design.
- **The preference-decay curve had two implementations** — `cli.ts` reimplemented `retrieval.ts`'s private `decayedConfidence`/`isDecayedBelowGroundTruth` against the same constants for `mem epoch --gc`'s report. Two copies of a formula drift, and this one decides whether the reported count matches the facts `recall` will actually downgrade. The retrieval helpers are now exported and the duplicate is gone.
- **`mem import --from-json` accepted unaddressable ids** — an imported `id` was only checked for presence, so a fact could be written with an id containing spaces, path separators, SQL wildcards, or shell metacharacters, which no `mem show`/`forget`/`edit` invocation can then address. Ids are now validated against the same hex/dash shape `resolveFactIdOrPrefix` uses, with a 128-character ceiling; a malformed id is reported as `skipped_error` for that fact rather than aborting the file.
- **The atomic-write temp file could outlive a failed write** — `writeManagedFile` wrote `<file>.token-goat-mem.tmp-<n>` and renamed it into place, but a failure between the two left the scratch file next to the managed file — in the user's project, or in their `~/.claude` — where no later run removed it. The write is now wrapped in a `try`/`finally` whose cleanup is best-effort and can never mask the original failure.
- **The token-goat integration seam behaved as if it were a one-shot process** — `buildHintFormat` opened the database with the bare `openDb`, which does not guarantee the storage-owned columns or the `sources`/`meta` tables exist, so reading a fact through it worked only by accident of which columns that path happens to select; it now uses `openStorage`. It also inherited `evaluateAnchor`'s process-lifetime memo, which is exactly right for the `mem` CLI (one query per process) and unbounded for an embedder holding the module across calls — there, the first verdict was served forever regardless of what changed on disk. Each call now starts from a cleared cache (`clearAnchorCaches`, the memo reset's new public name).

### Added

- **Default result limits on `mem list` and `mem recall`** — both now cap output at 20 by default, with a trailing `showing N of M -- use --limit to see more` line when truncated; `--limit <n>` overrides the default on either command. `mem recall`'s cap only ever applies to non-withheld results: a pending/contested/superseded/contradicted fact is never pushed out of the default output by unrelated clean facts outranking it, regardless of how many of those there are. `retrieve()` (`src/retrieval.ts`) now returns `{ results, totalNonWithheld, shownNonWithheld }` instead of a bare array, so callers can render the truncation trailer; `mem list --json`'s envelope gained `total`/`truncated` fields alongside its existing `facts`.

An ambiguous prefix errors and lists every matching id; a full id still resolves via the same fast exact-match path as before (`resolveFactIdOrPrefix` in `src/storage.ts`).
- **`--since-epoch <n>` on `mem recall`** — mirrors `mem review --since-epoch`: only includes facts written after write-epoch `n`, filtered at the SQL layer before ranking.

Confirm with `mem review --promote <id>`.

- **`mem import --from-json <path>`** — full-fidelity import of a `mem export` file: preserves each fact's original `id`, `status`, `confidence`, and `captured_at` exactly (unlike `--from-md`, which always imports as advisory `pending` candidates). Bypasses the capture pipeline's status/confidence defaulting (it calls `storage.insertFact` directly) but still runs the same secret screening before writing. Re-running the same import against the same store is idempotent: a fact whose `id` already exists is skipped as a duplicate, not re-inserted. `--from-md` and `--from-json` are mutually exclusive; exactly one is required.
- **`package-version <path> <name>@<version>` anchor predicate** — closes a real correctness gap: previously the only way to anchor a "we're on React 18" style fact was the brittle substring match `file-contains`. Deliberately fenced to a **declared-manifest check only**, never an installed/lockfile-resolved version check: it reads `path` (a `package.json`), looks up `name` in `dependencies` then `devDependencies`, and compares the declared range string against `expected` using only an exact-string match or a major-version-prefix match (e.g. declared `^18.2.0` affirms expected `18`) — no semver-range-satisfaction library, no lockfile parsing. Anything the comparison can't confidently resolve returns `unverified`, never a guessed `affirmed` (a predicate that can falsely affirm a version fact is worse than no predicate at all, per the anchor module's own three-valued-verdict design).
- **`mem export` filter flags** — `--kind`, `--status` (comma-separated), `--subject`, `--scope`, reusing `mem list`'s existing filter-parsing helpers verbatim. `mem export` now doubles as the stable, filtered, machine-readable query surface (previously it always dumped every fact regardless of status).
- **`--json` on `mem list` and `mem show`** — machine-readable output alongside the existing human-readable text (unchanged when `--json` is omitted). Shares the same fact projection `mem export` uses (`embedding` dropped, since it's large, usually null, and an internal retrieval-only detail). `mem show --json` additionally includes `freshness` (the anchor's current three-valued verdict) and `sources`, neither of which is part of the plain fact shape. **Stability policy: `--json` on `list`/`show` is explicitly unstable pre-1.0 — the shape may change without a major version bump. `mem export` is the stable, versioned (`schemaVersion`), machine-readable surface; prefer it for scripting.** `mem recall --json` is intentionally not included in this batch — its per-result annotations (freshness verdict, rank) are the genuinely volatile part of the data model.

### Changed

- **`mem recall`'s default (`--hint-style full`) output format** — each fact line no longer carries its own trailing CTA (`— mem show <id>` / `— resolve via mem review`); instead, one shared footer line (`mem show <id> for detail; mem review to resolve contested/pending`) is printed once after every fact line, when at least one fact was shown (mirrors the `--hint-format` TGMEM/2 wire format's existing footer-line precedent). `--hint-style terse` is unchanged (it already had neither CTA nor footer). **This is an intentional breaking change to `mem recall`'s default human-readable output text** — a script or human parsing the per-line CTA needs to adjust to the new footer line.

### Fixed

- **`mem remember --anchor`/`mem edit --anchor` rejected 6 of the 10 documented anchor predicates as "unknown predicate."** `capture.ts`'s `ANCHOR_ARITY` syntax-validation allowlist had drifted out of sync with `anchors.ts`'s actual predicate set, silently missing `file-contains`, `file-not-contains`, `newest-of`, `glob-exists`, `git-branch-is` — and would have shipped `package-version` (this release) with the same gap, reachable only via `mem import --from-json`, which bypasses this syntax gate. All ten predicates now validate correctly, including `newest-of`'s variable arity (`<expected> <candidate...>`, minimum 2 arguments).
- **`mem init` crashed with a raw error (not the `WiringConflictError` contract) on some hand-edited configs.** Two more spots that assumed well-formed input reached uncaught type errors instead of the documented "refusing to modify a hand-edited config" abort: (1) a `hooks.SessionStart` array element that is `null`, a primitive, or an object whose `hooks` isn't an array (`installClaudeSettings` threw `TypeError: Cannot read properties of null`; `uninstallClaudeSettings` likewise crashed instead of leaving the file untouched); (2) a `tasks.json` whose `tasks` or `inputs` key is present but not an array (`installTasksJson` reached jsonc-parser's raw `Can not add property to parent of type string`). Both now abort with `WiringConflictError` on install and are left untouched on uninstall, matching how the root/`hooks`/`SessionStart`-array checks already behaved.
- **`mem import --dry-run` created the database it claimed not to write.** The dry-run still opened mem's SQLite store, which runs `mkdirSync` + creates the db file, WAL sidecars, and schema on disk — so previewing an import in a project with no store yet silently created `~/.mem/mem.db`. The dry-run now runs entirely from the markdown file (`planImportFromMarkdown`) and opens no database, honoring the documented "nothing written".
- **Secret screening let unlabeled high-entropy secrets past through `anchor` and `sourceRef`.** A prior 0.2.0-era fix for the `sourceRef`/`anchor` path false-positive (see 0.2.0 below) overcorrected: `anchor` was exempted from the generic high-entropy heuristic field-wide instead of per-token, and `sourceRef` was excluded from screening entirely — including `SECRET_PATTERNS`. Since `mem remember --source-ref <ref>` accepts an arbitrary user/agent-supplied string (not just the programmatic `<path>:<line>` pointer `mem import` produces), a real credential placed in either field could be stored with zero screening. Both fields are now screened like any other: named `SECRET_PATTERNS` always run, and only a slash-containing token skips the generic entropy fallback (still avoiding the original path false-positive).
- **`mem edit` bypassed every field-level guard `mem remember` enforces.** Editing a fact's `--text`, `--subject`/`--value`, or `--anchor` went straight to storage with no length/emptiness checks and no anchor-syntax validation, so `mem edit` could store an over-length or empty text, or a malformed anchor (e.g. an unknown predicate) that `mem remember` would reject outright — the malformed anchor then permanently evaluates as "unverified" freshness. `mem edit` now runs the same validation `captureExplicit` does before writing. Also: a secret blocked by `mem edit` now writes an `edit_blocked_secret` audit_log entry, matching the audit trail both capture paths already wrote for a blocked secret.
- **`mem init copilot-vscode` crashed with a raw error on a `keybindings.json` containing literally `null`.** `installKeybindings` coerced the parsed root with `null ?? []`, which let a JSON `null` masquerade as an empty array, slip past the "not a JSON array" check, and reach jsonc-parser's `modify(text, [-1], …)` on a `null` root — throwing a raw `Can not add property to parent of type null` Error instead of the documented `WiringConflictError` contract. Every non-array root (`null`, number, string, boolean, object) now aborts with `WiringConflictError`, matching how `installTasksJson` rejects a non-object root. (This was the last JSON/JSONC wiring handler still carrying the coerce-instead-of-reject bug class.)
- **Contradiction detection collapsed same-subject facts from unrelated projects into one bucket.** `detectContradictions` keyed only on `subject` + `scope`, but mem's store is shared across every project, so `subject="package-manager" scope="project"` in project A (value `npm`) and the same subject/scope in project B (value `pnpm`) looked like a live contradiction. On the whole-store paths (`mem review`, `mem epoch --gc`, plain `mem recall`) this meant one project's fact was mislabeled — and, under `epoch --gc`, *persistently superseded* — because an unrelated project chose a different value. The bucket key now includes `scope_root` for non-global scopes (globals still share one bucket), so each project's facts stay independent. The `--hint-format` seam was already immune (it pre-filters to a single root before detection); this fixes every other caller.
- **`mem import --from-json` audit rows weren't written atomically with each fact insert.** A crash between the insert and its audit-log write could leave a fact with no audit trail. Every fact write in the import batch now happens in the same transaction as its audit row.
- **Markdown import let a stray closing fence marker leak fenced content into fact candidates.** A fenced block closed early by a mismatched marker was treated as ending the fence, letting subsequent fenced-block lines be scanned as bullet candidates. Fence tracking now remembers which marker opened the fence and only that marker can close it, per CommonMark/GFM.
- **`--age-days`/`--since-epoch` silently ignored non-numeric input instead of rejecting it**, and a missing/unreadable `mem import --from-md` file exited 2 (internal error) instead of 1 (user error). Both now fail loud with the correct exit code.
- **`mem import --from-json` crashed the whole transaction on an id duplicated within the same import file**, instead of skipping just that fact. Duplicate-within-file ids are now caught during planning and reported as `skipped_error`, matching how a duplicate against the existing store was already handled.
- **`mem import --from-json`'s structural-validation fix (this cycle) had regressed its own anchor-arity exemption**, rejecting multi-word substring anchors that had round-tripped correctly before. A narrower `validateFactFieldsOrThrow` (length/pairing checks only, no anchor-syntax gate) restores the exemption for JSON import while `mem edit`'s CLI-facing validation keeps the anchor-arity check.
- **A crash between a fact write and its audit-log write could leave any command's write with no audit trail**, not just `mem import`: `remember`, `suggest`, `edit`, `forget`, `pin`, `promote`, and `reject` all had the same gap. Every fact-write path now writes its status change and audit row in one transaction.
- **`updateFact`/`setFactStatus`/`deleteFact` bumped the global write epoch even when the target id didn't exist** (a no-op), producing a phantom epoch advance with nothing behind it. The epoch is now only bumped when a row actually changed.
- **`mem epoch --gc`'s contradiction-resolution status change and its audit-log row weren't written atomically**, the same gap already fixed elsewhere this cycle. Extracted a shared `setStatusWithAudit` helper (also now used by `forget`/`pin`/`promote`/`reject`, removing four near-duplicate implementations) so the fix and the dedup happened together.

- **`file-exists`/`file-absent`/`file-contains`/`file-not-contains`/`package-version` followed symlinks pointing outside the project root**, the same class of gap `glob-exists` already guarded against — a symlinked path could affirm or contradict an anchor based on content outside `--root`. All five now refuse a target reached through an out-of-root symlink.

- **JSON import accepted any string as `captured_at`**, not just genuine ISO-8601 timestamps — and the first attempt at this exact validation was itself dead code (it checked the ISO round-trip against nothing, so it never actually rejected anything). Fixed with a real string comparison against the canonical ISO form, the only format this codebase ever produces.
- **`file-newer-than` and `newest-of` still followed symlinks pointing outside the project root**, a carry-over gap left when the other five path-based predicates were fixed earlier this cycle. `newest-of` hard-contradicts if any candidate is a symlink escaping root, rather than silently skipping it (skipping could mask a genuinely newer file outside the sandbox).
- **`mem recall --context-files` silently did nothing when passed without `--hint-format`**, contradicting its own documented requirement. It now errors instead.
- **A stale anchor-error message listed only 4 of the 10 supported anchor predicates**, understating what the CLI actually accepts.
- **Precedence-tied facts that actually agreed on value were force-marked `contested`** just because a clearly-outranked fact in the same tie group disagreed — losing an unambiguous winner to a manufactured ambiguity. Only genuine ties (tied-precedence facts holding different values) are marked `contested` now; a tied group that agrees on value resolves normally, superseding only the facts that actually disagree.

Now surfaces the documented conflict error instead of crashing.

An embedding backend is an injectable seam; no concrete backend ships in v1 (BM25-only in practice).
- **`mem import --from-md <path>`** — advisory-only import: parses a markdown file (CLAUDE.md-style) for bullet-list lines that look like preference/decision-shaped statements and stores each as a **`pending`, `source_type: "derived"`** fact through the same `captureSuggested` trust path as any other suggested candidate — no code path writes `active`, and there is no bulk-promote shortcut; every imported fact still requires an explicit `mem review --promote <id>`. Bullets nested under an obviously structural heading (e.g. `Architecture`, `File Structure`) are skipped. Provenance (`<absolute file path>:<line>`) is recorded in the fact's `source_ref` field. `--dry-run` reports candidates without writing.
